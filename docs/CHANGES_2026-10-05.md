## 2. The database refuses impossible stock and money

New: `backend/alembic/versions/0039_money_and_stock_checks.py`.
Modified: `models/medicine_batch.py`, `sale.py`, `refund.py`, `purchase_order.py`,
`stock_take.py`. New shared list: `backend/app/core/integrity_rules.py`.

16 CHECK rules on 8 tables (values compared as stored integer cents):

- `medicine_batches`: stock and received quantity >= 0; cost and selling price >= 0
- `sales`: subtotal, discount, total >= 0
- `sale_items`: quantity > 0; 0 <= qty_refunded <= quantity; unit price, cost, line total >= 0
- `payments`: amount > 0
- `refunds`: total >= 0; `refund_items`: quantity > 0, price and line total >= 0
- `purchase_order_items`: quantity ordered > 0; received >= 0; costs >= 0
- `stock_take_items`: expected and physical count >= 0; close cost >= 0

Each rule matches what the API already validates, so normal use is unchanged.
Before, only careful code prevented these values; now the database rejects them
whatever wrote them (a future endpoint, a bad import, an edited restore file).

**The migration is atomic.** SQLite DDL is transactional but Alembic does not
wrap it. A fault test (reproduced, then fixed) showed a failure part-way left
a half-upgraded database: some tables constrained, revision still 0038, and
leftover `_alembic_tmp_*` tables that made every retry fail. The migration now
runs in one `BEGIN IMMEDIATE` transaction: it completes entirely, or the
database is exactly as it was. A permanent test injects that fault and asserts
nothing was left behind and a clean retry succeeds.

**Existing bad data is never altered, and never locks the shop out.** Before changing
anything the migration counts rows that already break a rule. If any exist it
stops, before touching the database. The launcher recognises exactly that
refusal and starts the app anyway on the current data (section 3); the upgrade is
retried at every launch and completes by itself once the rows are corrected. The
app also takes its pre-upgrade snapshot first.

**New read-only tool:** `python scripts/check_data_integrity.py <path to pharmacy.db>`
lists exactly which rows break which rule (opened in SQLite read-only mode; a
test proves the file's bytes are unchanged). Exit 0 clean, 1 problems, 2 cannot run.
Run it against real customer databases or backups BEFORE shipping an update.

**The three places that state the rules cannot drift:** a test asserts the
shared list, the model constraints and the migration's frozen copy are identical
(mutation-checked: changing one rule makes it fail).

## 3. The shop can never be locked out by these changes

`backend/desktop_main.py`, `pyinstaller/pharmacy-erp.spec`.

- **Refused migration does not stop the app.** If migration 0039 refuses because
  existing records break a rule (e.g. negative stock), the app starts normally on the
  unchanged data, writes `integrity-report.txt` (rule, count, row ids) next to the
  database, and logs it. This is allowed for exactly one situation (upgrading from
  revision 0038 to head 0039, where the new rules only add protection); any other
  migration failure, or any later migration, is still fatal by design. Tests
  fault-inject a different failure to prove it.
- **Stray machine settings are ignored.** Other software can leave variables such as
  `ENVIRONMENT` set machine-wide. The launcher only filled in absent settings, so a
  stray value would win and the new startup validation would refuse to open the app.
  The launcher now drops any `ENVIRONMENT`, `REDIS_MODE`, `JWT_SECRET_KEY` or
  `ENCRYPTION_KEY` that validation would reject (and always ignores
  `WEB_CONCURRENCY`, meaningless to the single in-process server), logging only the
  setting's name, never its value. Usable values set on purpose are left alone.
- The migration now imports one small module (`app.core.integrity_rules`); it is
  listed explicitly in the PyInstaller spec, and a frozen build was run to confirm.

## 4. Bad configuration fails at startup

`backend/app/core/config.py`. The app now refuses to start, with the fix command
in the message, when:

- `JWT_SECRET_KEY` is under 32 characters or is a `changeme...` placeholder;
- `ENCRYPTION_KEY` is not base64, not exactly 32 bytes, or all zeros
  (previously a bad key failed only on the first backup or AI-key save);
- `ENVIRONMENT` is not development / staging / production (a typo like `prod`
  silently skipped production behaviour);
- `REDIS_MODE` is not `redis` / `memory`, or is `memory` with `WEB_CONCURRENCY > 1`
  (each worker would silently get its own private cache and rate limits).

Desktop installs are unaffected: the launcher only ever generated 64-hex JWT
secrets and 32-byte random keys. Only a hand-edited `.env` / `secrets.json`
with a weak value is stopped.

**Mistake caught and fixed in my own earlier change:** the README's dev setup
(`JWT_SECRET_KEY="dev-secret-change-me"`, zero encryption key) and
`scripts/load_test.py` (`"load-test-secret"`) would have failed this new
validation. README, load test, `conftest.py` and all three CI jobs now use valid
fixed sample values, and a test asserts the README's documented values pass.

## 5. Two silent-failure paths fixed

- `api/v1/auth.py` (token refresh): if the forced-password-change flag could not be
  read, it answered "no change needed", silently skipping a security prompt. It now
  logs the error and answers "change required" (fail closed), while still completing
  the refresh so the session is not lost.
- `core/business_time.py`: an unusable saved timezone fell back to UTC silently,
  which shifts every report day. It still falls back (reports must not break) but
  now logs a warning naming the bad value.

All 21 broad `except Exception` handlers were reviewed. The ones on money, data and
security paths were read in full (restore rolls back and re-raises; the notification
loop must survive one bad message; unreadable spreadsheets become a clean 400;
post-sale side effects are logged and cannot undo a committed sale). The remaining
cosmetic or enrichment fallbacks (receipt logo and timezone, AI-assistant context,
websocket cleanup) were judged by their documented purpose and left as they are.

  require the `Pharmacy-ERP-Setup-` prefix and `.exe`) can never mistake it for the

**Effect:** a pull request adding a vulnerable dependency, or a push after a new
advisory lands, now fails CI; expect occasional unplanned dependency bumps. The audit
steps need network access to the PyPI / npm advisory services; a transient outage
fails a run and a re-run fixes it.

## Known limits that remain (not time bombs, but you should know)

1. **The in-app updater does not verify the installer it downloads, and the installer
   is not code-signed.** Checksums are now published (section 6) but the app does not
   check them. Doing that means changing the Electron download / install-launch code,
   which cannot be tested without a Windows GUI session, so it was deliberately not
   changed blind. Code signing needs a certificate that only you can buy.
2. **If a customer's existing data already breaks a rule, the new database rules are not
   applied until the rows are corrected.** The shop keeps running normally on its
   unchanged data; `integrity-report.txt` and the checker script list the rows. Nothing
   is silently "repaired". A restore of an old backup that contains such rows would be
   rejected by the database and rolled back (restore is transactional); this path was
   read but not tested.
3. **Loyalty points are awarded after the sale commits.** A failure there is logged and
   the sale stands, but that customer's points for that sale are not awarded. Moving it
   into the sale transaction would let a loyalty bug block a sale at the counter.
4. **Changing the business timezone re-buckets historical report days.**
5. `CHANGELOG.md` still contains only version headings.
